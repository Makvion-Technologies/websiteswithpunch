502, 503 and 504 errors all mean "the server side failed", and people often treat them as the same thing. They aren't. Each code points to a different part of the request path and a different kind of failure. Reading them correctly saves a lot of guesswork.

This guide explains what each code means according to the HTTP standard, where in your setup it comes from, and how to fix it.

## The short version

HTTP status codes are defined in [RFC 9110](https://www.rfc-editor.org/rfc/rfc9110) (HTTP Semantics). In plain terms:

| Code | Name | What it means | Who usually sends it |
| --- | --- | --- | --- |
| 500 | Internal Server Error | The application hit an error it didn't handle | Your app |
| 502 | Bad Gateway | A proxy got an invalid response, or none at all, from the server behind it | Reverse proxy, load balancer, CDN |
| 503 | Service Unavailable | The server can't handle the request right now: overload or maintenance. It may include a `Retry-After` header | App, web server, host, load balancer |
| 504 | Gateway Timeout | A proxy gave up waiting for the server behind it | Reverse proxy, load balancer, CDN |

The key word in 502 and 504 is **gateway**. These errors come from something sitting *in front of* your application, reporting that the thing behind it misbehaved.

## Where each error comes from

::fig proxy-chain

A typical modern request passes through several hops: browser → CDN → reverse proxy (Nginx, a load balancer) → application server (PHP-FPM, Node, Python) → database. The hop that *generates* the error page is usually not the one that's broken. It's the one reporting on the hop behind it.

- **502:** the next hop refused the connection, closed it suddenly, or sent back something that wasn't valid HTTP.
- **504:** the next hop accepted the connection but didn't answer in time.
- **503:** something decided not to serve the request at all. That's often deliberate: maintenance mode, a full queue, no healthy servers left behind a load balancer.

## Fixing 502 Bad Gateway

Start with the proxy's error log, because it names the cause:

```bash
sudo tail -n 50 /var/log/nginx/error.log
```

| Log message (Nginx) | Cause | Fix |
| --- | --- | --- |
| `connect() failed (111: Connection refused) while connecting to upstream` | The app isn't running or listens on a different port | Start or restart the app; check the `proxy_pass` / `fastcgi_pass` address |
| `connect() to unix:/run/php/php-fpm.sock failed (2: No such file or directory)` | Wrong PHP-FPM socket path, often after a PHP version upgrade | Point Nginx at the new socket (e.g. `php8.3-fpm.sock`) |
| `... (13: Permission denied) while connecting to upstream` | Nginx can't open the socket | Fix the socket owner/group (`listen.owner`, `listen.group` in the FPM pool) |
| `upstream prematurely closed connection` | The app crashed while handling the request | Read the app's own log; check for out-of-memory kills (`dmesg \| grep -i kill`) |
| `upstream sent too big header` | Response headers (often large cookies) exceed the buffer | Raise `proxy_buffer_size` / `fastcgi_buffer_size` |

Then check that the app process is alive and listening:

```bash
sudo systemctl status php8.3-fpm     # or your app's service name
sudo ss -ltnp | grep -E ':(3000|8000|9000)\s'
```

Behind a CDN, 502-style errors carry the CDN's own codes. On Cloudflare, **521** means your web server refused the connection, **522** means the connection timed out, and **520** means the origin returned something unexpected. All three point at your origin server, not at Cloudflare.

## Fixing 503 Service Unavailable

A 503 is often deliberate, so ask "who decided to refuse?" first.

1. **Maintenance mode left on.** WordPress puts a `.maintenance` file in the site root during updates and shows "Briefly unavailable for scheduled maintenance" with a 503. If an update was interrupted, the file stays and so does the error. Delete the file to fix it.
2. **Worker pool exhausted.** PHP-FPM logs `server reached pm.max_children setting`. Every worker is busy and new requests wait in a queue or get refused. Find out *why* requests are slow (usually the database) before you raise the limit. More workers on a struggling database just make it worse.
3. **Host resource limits.** Shared and managed hosts return 503 when an account goes over its CPU, memory or process limits. The control panel normally shows this.
4. **No healthy servers behind a load balancer.** If every backend fails its health check, the balancer has nowhere to send traffic. Fix the backends, then check that the health check URL itself is cheap and correct.
5. **Rate limiting.** Some setups use 503 for rate limiting rather than the more specific 429.

## Fixing 504 Gateway Timeout

The proxy waited and gave up. Nginx's default `proxy_read_timeout` and `fastcgi_read_timeout` are 60 seconds. Cloudflare's 524 error means its own 100-second proxy timeout was reached.

- **Find the slow request.** The access log (with `$request_time` and `$upstream_response_time` in the log format) shows which URLs take longest.
- **Fix the slow part, usually the database.** Look for missing indexes, an expensive report on every page load, or a lock held by a long job. Turn on the slow query log.
- **Look at external calls.** A page that calls a payment API, a CRM or a slow third-party service waits as long as that service does. Set short timeouts on outgoing calls.
- **Move long work to the background.** Imports, exports and bulk emails belong in a job queue, not in a web request.
- **Raise the timeout only as a last resort,** and only for the specific route that needs it. A higher global timeout hides the problem and ties up workers longer.

## A five-minute triage routine

When a 5xx page appears and you don't know why, this order finds the cause fastest:

1. **Read the status code and who served it.** A Cloudflare-branded 52x page, a plain Nginx page or your app's own error template each point to a different hop.
2. **Check whether it's every page or some.** If static files load but dynamic pages fail, the web server is fine and the app or database is the problem.
3. **Read the proxy's error log**, then the app's log, for the minutes around the first failure.
4. **Check resources:** `df -h` (disk), `free -m` (memory), `uptime` (load), and whether the out-of-memory killer has struck (`dmesg | grep -i kill`).
5. **Ask what changed.** A deploy, a plugin update, a traffic spike, a config edit or a provider incident accounts for most 5xx outages. Roll back first and investigate after.

### When it's your host's problem

If none of your logs show anything, the error may come from infrastructure you don't control: the host's load balancer, a shared server, or a platform outage. Check the host's status page and support channels. Note the exact times, codes and URLs that fail, because a support ticket with that detail gets answered much faster than "my site is down".

## Why these errors matter for search

Google's crawling documentation says 5xx responses make Googlebot slow down its crawling, and URLs that keep returning server errors are eventually dropped from the index. A few minutes of 502s won't hurt rankings. Days of on-and-off errors can. For planned downtime, return a 503 with a `Retry-After` header and keep it short. The details are in [website maintenance without hurting SEO](/blog/website-maintenance-without-hurting-seo).

## Catch them before your users do

These errors are often intermittent. A 504 that only appears under evening load won't show up when you test at lunchtime. Outside monitoring records the status code over time so patterns become visible:
